# Antigravity headless invocation — research findings

> **New convention note:** `docs/research/` did not exist in this repo before this file. There was no prior research-notes convention (only `docs/agents/` existed, covering agent-skill behavior). This document establishes `docs/research/` as a place for primary-source investigation notes; it is not following an existing pattern.

## Summary

This document investigates whether Google Antigravity (Google's agentic IDE built on Gemini 3, publicly launched November 2025) can be invoked headlessly from a local HTTP router, the way the `claude` CLI already is in this project. Research was conducted on 2026-07-19 using primary sources: Antigravity's official GitHub organization (`google-antigravity`), its `antigravity-cli` repository (README, `CHANGELOG.md`, and GitHub Issues filed against the official repo), Google's official Codelabs site, and the Gemini API documentation on `ai.google.dev`. Where a claim rests on a GitHub Issue rather than first-party documentation, this is called out explicitly — issues are real, verifiable reports of behavior against the official binary, but they are user-filed, not Google's own spec, and are weighted accordingly below.

All sources were fetched directly (via `curl`, the GitHub API, or `WebFetch`) and cross-checked against each other during this research session; URLs and repo metadata (org creation date, release timestamps, issue states) were verified independently rather than taken solely from search-result summaries.

## Question 1: Does Antigravity expose a local CLI?

**Answer: Yes.** Antigravity ships a dedicated CLI binary, distinct from the IDE/GUI application, called **Antigravity CLI**, invoked via the command **`agy`**.

- The official GitHub organization is `google-antigravity` (org id `242056456`, created 2025-11-04, matching Antigravity's public November 2025 launch) ([github.com/google-antigravity](https://github.com/google-antigravity)). Note: the org does not carry GitHub's domain-verified badge (`is_verified: false` in the GitHub API response as of 2026-07-19), so this is inferred to be official from naming, launch-date alignment, and content, not from GitHub's own verification mechanism.
- The `antigravity-cli` repository's README states: "Antigravity CLI understands your codebase, makes edits with your permission, and executes commands — right from your terminal," and gives `agy` as the launch command, plus install scripts (`curl -fsSL https://antigravity.google/cli/install.sh | bash` for macOS/Linux) ([github.com/google-antigravity/antigravity-cli README](https://raw.githubusercontent.com/google-antigravity/antigravity-cli/main/README.md)).
- Google's own Codelabs site (`codelabs.developers.google.com`, an official Google domain) has a hands-on tutorial confirming installation, an OAuth-based login menu ("Select login method: 1. Google OAuth 2. Use a Google Cloud project"), and basic invocation of `agy` ([Hands-on with Antigravity CLI | Google Codelabs](https://codelabs.developers.google.com/antigravity-cli-hands-on)).
- The README describes `agy` as a **Terminal User Interface (TUI)** by default, positioned as the terminal-first counterpart to the full "Antigravity 2.0" GUI application, sharing the same agent engine and settings.

**Confidence: High** for existence and invocation (`agy`); **medium** on official/first-party status specifically because of the missing GitHub org verification badge — the balance of evidence (org name, creation date, description, `antigravity.google` cross-links in the README) strongly favors official, but this one data point is a gap.

## Question 2: Does it support a non-interactive/headless "print" mode?

**Answer: Yes**, via a `-p` / `--print` flag, analogous in shape to Claude Code's `-p`/`--print` — but with a documented history of reliability bugs around non-TTY output that a router built on it should account for.

- Google's official Codelabs tutorial shows the exact pattern: `agy -p "What is the gcloud command to deploy to Cloud Run"`, describing it as executing "a prompt directly and returns output, useful for scripted automation where follow-up conversation isn't needed" ([Antigravity CLI Codelab](https://codelabs.developers.google.com/antigravity-cli-hands-on)).
- The CLI's own `CHANGELOG.md` (fetched from the repo's `main` branch) references `-p`/`--print` as an established, actively maintained mode across many releases, e.g.:
  - v1.1.4: "Fixed headless (`-p` / `--print`) runs so they now honor persisted `settings.json` policies, including permissions, file access, sandbox mode, auto-execution, and artifact review."
  - v1.1.2: "Added support for pasting the OAuth authorization code in print mode (-p) ... and made truly headless runs fail fast with an actionable message instead of blocking."
  - v1.1.1: "Fixed print mode (`--print` / `-p`) silently exiting with a success code and empty output when a request failed server-side, now writing the error to stderr and returning a non-zero exit code." Also: "Fixed `agy -p` hanging when run inside a shell script or subprocess by no longer reading stdin when a prompt is provided via a flag."
  - v1.0.6: "Fixed `--sandbox` flag propagation in headless print mode (`-p` / `--print`)."
  ([CHANGELOG.md](https://raw.githubusercontent.com/google-antigravity/antigravity-cli/main/CHANGELOG.md))
- **Caveat — a real, verified reliability gap:** GitHub Issue #76 on the official repo, "`agy --print` / `-p` silently drops stdout when run with a non-TTY (pipe, subprocess, redirect)" (opened 2026-05-21, closed 2026-07-12), reports that piping/redirecting `agy -p`'s output produced zero bytes on stdout and stderr despite a real model round trip completing, across Windows shells (Git Bash, PowerShell, cmd.exe) ([Issue #76](https://github.com/google-antigravity/antigravity-cli/issues/76), verified directly via the GitHub API, not just a search summary). This is precisely the failure mode an HTTP router would hit if it shells out to `agy -p` and captures stdout via a subprocess pipe — which is the standard way such a router would invoke any CLI. The issue is now closed, and the changelog shows related non-TTY output fixes (e.g., v1.0.15: "Fixed a bug on Windows where print mode and other non-TUI command outputs were silently discarded when run in non-TTY environments (such as pipes or subprocesses)"), but this research did not confirm the exact commit/version that closed Issue #76 specifically, so treat "fixed as of the latest CLI version (1.1.4, released 2026-07-18)" as **likely but not fully confirmed**.
- No official flag reference/table (equivalent to Claude Code's `--help` output or a documented CLI flags page) was found in static form — `antigravity.google/docs/*` is a client-rendered single-page app and did not yield readable content via direct HTTP fetch; the flag inventory above is reconstructed from the changelog and Codelabs example rather than a single canonical reference page.

**Confidence: High** that `-p`/`--print` exists and works in recent versions; **medium** on exactly how robust it is in all environments today, given the documented history of non-TTY bugs spanning at least six point releases.

## Question 3: Does it support resuming a specific conversation/session by ID?

**Answer: Partially.** A `--conversation` / `-c` flag exists and can resume a specific prior conversation in headless mode, but there does not appear to be a documented way for an external caller to mint a conversation ID up front and have the CLI create-or-resume against that exact ID — which is the shape a stateless HTTP wrapper actually needs.

- The CLI changelog confirms the flag's existence and that it works in headless mode: v1.0.9 — "Fixed a bug in headless print mode resumption (`--conversation`/`-c` `-p ...`) where the CLI would dump the entire historical conversation transcript instead of only printing the newly generated response." ([CHANGELOG.md](https://raw.githubusercontent.com/google-antigravity/antigravity-cli/main/CHANGELOG.md)). This confirms `--conversation <id>` / `-c` combined with `-p` is a real, exercised code path for resuming a specific conversation non-interactively.
- However, GitHub Issue #7 on the official repo, "feat(--print): emit per-conversation ID so headless callers can resume specific sessions" (opened 2026-05-19, still open as of this research), states directly: "the conversation's identifier is never surfaced in stdout, stderr, or any documented file. The CLI does support `--conversation <id>` to resume a specific prior conversation, but there's no way to *capture* the ID from a `--print` run in the first place." The issue also notes `-c`/`--continue` resumes the *most recent* conversation globally on the machine — useful for one interactive user, but unsafe for a router juggling multiple concurrent conversations, since concurrent callers would cross-contaminate each other's "most recent" conversation. The issue proposes (unresolved, as of 2026-07-19) letting `--conversation <id>` create a new conversation under a caller-chosen ID, mirroring Claude Code's `--session-id` ([Issue #7](https://github.com/google-antigravity/antigravity-cli/issues/7), verified directly via the GitHub API).
- This is a GitHub Issue, not first-party documentation — it is strong *evidence* of current behavior (filed with specific repro details, environment info, and a clear description of the existing `--conversation`/`-c` mechanics), but it is a third-party bug report, not a Google spec statement, and the feature it requests may since have shipped without this research catching a corresponding changelog entry.

**Confidence: Medium.** The existence of *some* form of `--conversation`/`-c`-based resume is well-supported (changelog + issue agree). The specific claim that there is no supported way to pre-assign a session ID for a stateless multi-tenant caller rests on a single (open) GitHub issue as of the research date, and could be stale if a later CLI release closed the gap without a changelog entry this research surfaced.

## Question 4: How does local authentication work?

**Answer: Local OAuth (Google Sign-In) session, backed by the OS keyring, reused transparently across CLI invocations** — the same general shape as Claude Code's `claude login`.

- The repository README states: "The CLI authenticates via the system keyring, falling back to Google Sign-In if no active session exists," with distinct flows for local (auto-opens the default browser) and remote/SSH (prints an authorization URL to complete login locally), and a `/logout` command to clear credentials ([README.md](https://raw.githubusercontent.com/google-antigravity/antigravity-cli/main/README.md)).
- The official Codelab confirms the interactive first-run experience presents a menu — "Select login method: 1. Google OAuth 2. Use a Google Cloud project" — with the OAuth path performing standard browser-based sign-in and the user pasting a code back into the terminal ([Antigravity CLI Codelab](https://codelabs.developers.google.com/antigravity-cli-hands-on)).
- The changelog corroborates that the keyring-backed session is meant to persist and be reused automatically, and specifically addresses headless/container environments: v1.1.3 — "Fixed repeated sign-in prompts on Linux caused by the OS keyring: the CLI now bypasses the keyring when no D-Bus session bus is present (headless hosts and containers), skips it for an hour after a timeout, and uses longer keyring timeouts so a slow-but-successful credential read is no longer cut short and forced into a fresh login." v1.0.1: "Fixed OAuth token persistence and authentication hangs." ([CHANGELOG.md](https://raw.githubusercontent.com/google-antigravity/antigravity-cli/main/CHANGELOG.md))
- No evidence was found that headless/scripted use of `agy -p` *requires* a separate Gemini API key for ordinary (consumer/free-tier) use — the README and changelog both describe the keyring/OAuth session as the standard credential path, with a separate "G1 credits" mechanism (v1.0.3 changelog) as a paid quota top-up, not a distinct auth scheme, and a documented "Use a Google Cloud project" option at onboarding for enterprise use.

**Confidence: High.** Multiple independent official/near-official sources (README, Codelab, changelog across several versions) agree on the OAuth+keyring model and on it being designed to survive across headless/CI/container contexts as of recent CLI versions.

## Question 5: Does the Gemini API expose an OpenAI-compatible endpoint, and does it share Antigravity's credential?

**Answer: Yes, an OpenAI-compatible endpoint exists — but it requires a distinct Gemini API key, not Antigravity's local OAuth session.**

- The official Gemini API docs confirm an OpenAI-compatible endpoint at base URL `https://generativelanguage.googleapis.com/v1beta/openai/`, which serves an OpenAI-SDK-shaped `chat.completions.create(...)` surface (and a `POST https://generativelanguage.googleapis.com/v1beta/openai/chat/completions` REST form). Verified directly by fetching and parsing the raw page content (not just a summarized fetch): the documented curl example is `curl "https://generativelanguage.googleapis.com/v1beta/openai/chat/completions" -H "Authorization: Bearer $GEMINI_API_KEY" ...` ([OpenAI compatibility | Gemini API | Google AI for Developers](https://ai.google.dev/gemini-api/docs/openai)).
- The same page states the only changes needed to point an OpenAI client at Gemini are `api_key="GEMINI_API_KEY"`, `base_url="https://generativelanguage.googleapis.com/v1beta/openai/"`, and a compatible `model` name — i.e., the credential is explicitly a **Gemini API key** obtained from Google AI Studio, not an OAuth session.
- The Gemini API does separately support OAuth as an *alternative* to an API key, per Google's own quickstart: "The easiest way to authenticate to the Gemini API is to configure an API key... If you need stricter access controls, you can use OAuth instead." But this OAuth path requires the caller to **set up their own Google Cloud project, OAuth consent screen, and a self-registered OAuth Client ID**, downloading a `client_secret.json` and managing a `token.json` — a distinct, developer-provisioned credential, not a transparent reuse of Antigravity's own consumer sign-in session ([Authentication with OAuth quickstart | Gemini API | Google AI for Developers](https://ai.google.dev/gemini-api/docs/oauth)). There is no indication in either page that Antigravity's own keyring-stored OAuth token is usable as a bearer credential against this endpoint — they are separate OAuth clients/consumers from Google's perspective, and Antigravity's own docs make no mention of exposing its token for external reuse.
- **Notable finding for future reference, outside the original scope but visible in the fetched docs banner:** both the OpenAI-compatibility page and the OAuth quickstart page currently display the banner "The Interactions API is now generally available. We recommend using this API for access to all the latest features and models," suggesting Google is steering developers toward a newer first-party "Interactions API" rather than the OpenAI-compatibility shim for new integrations. This research did not investigate the Interactions API further; it is flagged here because it may be a better long-term integration target than either CLI-wrapping or the OpenAI-compat shim, and is a natural next research task if the router pursues a direct-API integration for the Antigravity/Gemini leg.

**Confidence: High** on the endpoint's existence, shape, and API-key requirement (directly verified from the raw served HTML of `ai.google.dev`, not a search summary). **High** on OAuth being a separate, self-provisioned credential rather than Antigravity's session. **Low confidence, not investigated** on the newer "Interactions API" — flagged, not researched.

## Implications for the router design

1. **A headless CLI path for Antigravity is plausible, unlike a hard "no CLI exists" finding.** `agy -p "<prompt>"` is a real, actively maintained, documented headless mode, structurally similar to `claude -p`. The router's Claude-Code-shaped architecture (shell out, capture stdout, parse a result) is not fundamentally blocked for the Antigravity leg.

2. **But the CLI path is meaningfully less mature and less well-specified than Claude Code's, and a router should not assume parity.** Concretely:
   - **Non-TTY stdout reliability has a documented history of bugs** (Issue #76, and multiple changelog entries across six-plus point releases fixing related non-TTY/headless issues). A router that spawns `agy -p` as a subprocess and reads stdout via a pipe is exactly the scenario that has broken in the past. Before relying on this, the router should pin a specific `agy` version, add its own timeout/retry/empty-output detection, and treat "exit 0, empty stdout" as a suspicious result requiring a retry or error surfaced to the caller — not assume success.
   - **There is no clean, documented equivalent of `--session-id` for pre-assigning a conversation ID.** The existing `--conversation`/`-c` mechanism can resume a *known* conversation, but (per the one open GitHub issue found) there's no first-party way for an external caller to learn or choose that ID from a `--print` invocation. This is the single biggest architectural gap relative to Claude Code's `--resume`/`--session-id` model. Practical options for the router, in rough order of preference given current evidence:
     - Treat this as **not yet reliably supported** and only offer single-turn (stateless) Antigravity requests through the router until the CLI exposes a caller-assignable ID — i.e., degrade gracefully rather than building multi-turn state on an undocumented mechanism.
     - If multi-turn is required now, investigate the undocumented `~/.antigravitycli/` per-workspace files mentioned in the GitHub issue as a possible (fragile, unsupported) way to recover the assigned ID after a first turn — accepting this could break on any CLI update since it relies on undocumented internal state.
     - Re-check `agy --help` / the changelog against whatever CLI version is actually installed before committing to either path, since this is an actively developed area (the changelog shows conversation/print-mode changes as recently as the newest release, 1.1.4, 2026-07-18).
   - **Authentication reuse works in the router's favor.** Like Claude Code, Antigravity's local OAuth session is meant to persist via the OS keyring and be reused transparently by CLI invocations, including from headless/container contexts (explicitly hardened for that case as of v1.1.3). This means the router likely does not need separate credential management for the Antigravity leg beyond ensuring `agy` has been logged in once on the host — mirroring how it presumably handles `claude login`.

3. **The Gemini API's OpenAI-compatible HTTP endpoint is a real, documented alternative to CLI-wrapping — but it is a different integration than "drive the user's logged-in Antigravity session."** It requires its own Gemini API key (or a separately provisioned OAuth client), which:
   - Is architecturally simpler and almost certainly more robust than shelling out to `agy` (no TTY/subprocess quirks, official request/response contract, already OpenAI-`/v1/chat/completions`-shaped — which is convenient since the router's own exposed endpoint is also OpenAI-compatible).
   - But it is **not the same thing as routing through the user's local Antigravity/Gemini 3 session** — it's a direct Gemini API call using a separately obtained API key, bypassing Antigravity (and any Antigravity-specific agent orchestration, tool use, or IDE-context features) entirely. If the point of the "Antigravity" leg of the router is specifically to reuse Antigravity's agentic behavior (file edits, tool calling, IDE-aware context) rather than "just call a Gemini model," this path does not deliver that — it would deliver a bare Gemini chat completion, architecturally closer to just adding "Gemini API" as a third provider than to "route into an existing Antigravity session."
   - If the router's actual goal for the Antigravity leg is "get a reply from Gemini 3 with minimal fuss," the OpenAI-compatible endpoint is very likely the better engineering choice today. If the goal is specifically "drive the same headless Antigravity CLI/agent session a developer would otherwise use interactively," the router is stuck with `agy -p`'s current rough edges (point 2 above) and should budget for that immaturity.

4. **Bottom line:** headless invocation of Antigravity is feasible, not blocked outright — but it should be built with explicit failure handling for empty/non-TTY output, and with an honest scoping decision (stateless-only, or accept an unsupported/fragile ID-recovery mechanism) for multi-turn conversations, pending either a CLI feature update or further testing against the actual installed `agy` version.
